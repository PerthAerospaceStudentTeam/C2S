## Dialight RGB LED

The [Dialight 5050 PLCC-4 Addressable RGB LED](https://s3-us-west-2.amazonaws.com/catsy.557/Dialight_datasheet_587-2054-127F_Addressable_RGB.pdf) is an 8-bit RGB LED that uses a one-wire interface.

### Basic Methods

| Function | Basic Description |
| :--- | :--- |
| `RGB_SetColour(r,g,b)` | Sets the LED to the specified 8-bit RGB value |
| `RGB_Reset()` | Clears the LED |

### Important Notes

> [!IMPORTANT]
> Only 8-bit (0-255) values are supported per colour channel.

## INA219BIDR Current Sense Amplifier

The [INA219BIDR](https://www.ti.com/lit/ds/symlink/ina219.pdf?ts=1790292975610) is a current sense amplifier (CSA) that allows you to monitor the real-time power, current, and voltage of the board.

### Core Variables

- `hi2c`: The I2C handle generated by CubeMX
- `INA219_HandleTypeDef`: A struct that tracks device configuration and calculated telemetry:
    - `*hi2c`: Pointer to the I2C handle
    - `current_lsb`: Calculated current LSB resolution used for unit conversion
    - `calibration`: Value written to the INA219 calibration register
    - `shunt_voltage`: Raw shunt voltage register value
    - `bus_voltage`: Raw bus voltage register value
    - `power`: Raw power register value
    - `current`: Raw current register value
    - `current_mA`: Converted load current in milliamperes (mA)
    - `power_mW`: Converted power consumption in milliwatts (mW)

### Basic Methods

| Function | Basic Description |
| :--- | :--- |
| `INA219_Setup(*INA219, *hi2c);` | Configures the chip based on settings in `INA219`. |
| `INA219_ReadAll(*INA219)` | Completes readings and conversions and stores results in `INA219`. |

### Basic Usage Example

```c
#include "ina219.h"

I2C_HandleTypeDef hi2c;
INA219_HandleTypeDef INA219_Chip;
INA219_Setup(&INA219_Chip, &hi2c);

// Read CSA Data
INA219_ReadAll(&INA219_Chip);

// Grab power (mW) and current (mA):
float power = INA219_Chip.power_mW;
float current = INA219_Chip.current_mA;

```

### Important Notes

> [!NOTE]
> The INA219 gain and shunt resistance is defined in `config.h`.

## AT25xF2561C QSPI Flash Memory Driver

Custom STM32 HAL-based QSPI driver for the **Renesas [AT25xF2561C](https://au.mouser.com/datasheet/3/1166/1/REN_DS_AT25SF2561C_AT25QF2561C_199I_DST_20260108.pdf)** (256 Mbit / 32 MB) QSPI Flash memory chip. This driver abstracts low-level STM32 HAL QSPI commands into an intuitive API for reading, writing, and erasing data chunks specifically for C2S development.

### Core Variables

- `hospi`: The OctoSPI handle generated by CubeMX.
- `sCommand`: A command struct for OctoSPI functions.
- `QSPI_HandleTypeDef`: A struct that tracks chip information like,
    - `occupied_data`: How much data has already been written
    - `memory_size`: how many bytes the chip can hold
    - `ID_REG[3]`: The manufacturing ID
    - `*hospi`: Pointer to the OctoSPI handle
    - `*sCommand`: Pointer to the command struct
- `QSPI_DataBlock_HandleTypeDef`: A struct that tracks information for an image to be written to memory.
    - `data_size`: How large the data is in bytes
    - `*tx_pData`: Pointer to the data source
    - `*rx_pData`: Pointer to the data destination (where it will be read back into)
    - `address_block_start`: Where in QSPI the data starts
    - `address_block_end`: Where in QSPI the data ends

### Basic Methods

| Function | Basic Description |
| :--- | :--- |
| `QSPI_Init_Memory(*hospi, *sCommand, *QSPI_Memory)` | Configures the QSPI memory and populates `QSPI_Memory`. |
| `QSPI_Init_DataBlock(*DataBlock, data_size, *tx_pData, *rx_pData)` | Preps the image for transfer by populating `DataBlock` with the memory to be written `tx_pData` and the location where it will eventually be read back into `rx_pBuffer`.|
| `QSPI_Write_Data(*QSPI_Memory, *DataBlock)` | Writes `tx_pBuffer` to `QSPI_Memory`. |
| `QSPI_Read_Data(*QSPI_Memory, *DataBlock)` | Reads data into `rx_pBuffer` from `QSPI_Memory`. |
| `QSPI_Erase_Data(*QSPI_Memory, *DataBlock)` | Clears `DataBlock` from QSPI memory |

### Basic Usage Example

```c
#include "AT25xF2561C.h"

uint8_t tx_data[] = "IMAGE_DATA_001";
uint8_t rx_buffer[sizeof(tx_data)];

OSPI_HandleTypeDef hospi1;
QSPI_HandleTypeDef QSPI_Memory;
OSPI_RegularCmdTypeDef sCommand;
QSPI_DataBlock_HandleTypeDef DataBlock;

// Initialise driver hardware & configuration
QSPI_Init_Memory(&hospi1, &sCommand, &QSPI_Memory);

// Prepare data chunk (Source, Destination, Size)
QSPI_Init_DataBlock(&DataBlock, sizeof(tx_data), tx_data, rx_buffer);

// Write to memory
QSPI_Write_Data(&QSPI_Memory, &DataBlock);

// Do some stuff...

// Read back data
QSPI_Read_Data(&QSPI_Memory, &DataBlock);

// Clear data
QSPI_Erase_Data(&QSPI_Memory, &DataBlock);

```

### Important Notes

> [!CAUTION]
> If you are finished with data, make sure to erase it, otherwise a memory leak will occur!

> [!IMPORTANT]
> The driver uses a **Last-In, First-Out (LIFO)** stack architecture managed by `occupied_data` inside the `QSPI_Memory` handle. It was designed around storing a single image, so if you store several items, make sure you abide by stack rules (writing/erasing in reverse order). You can read data from any position though.

> [!NOTE]
> At the time of `QSPI_Init_DataBlock`, you don't need to have specified `rx_pData` as it is only accessed when calling `QSPI_Read_Data`, if need be, you can leave it as `void`. The same goes for `tx_pData`.

> [!NOTE]
> Data can be left in its original types as it is cast to the required type during read/write e.g., if you want to write a character and read it back later, you can set the `rx` and `tx` locations as `char`.
